# Traduire GitQuest

GitQuest sépare deux choses :

1. **l'interface** (navigation, boutons, messages, explications, aide terminal) ;
2. **le contenu pédagogique** (cours, missions, briefings, histoires).

L'interface et le contenu pédagogique sont livrés en français et en anglais.
La langue se change sans rechargement : l'interface vient des catalogues i18n,
le contenu d'un catalogue de textes fusionné avec la structure française.

Le document (`lang`, titre, description), le sélecteur de langue et le manifeste
PWA sont également pris en charge. Le manifeste reste unique (limite de la PWA) :
il est rédigé en anglais, tandis que le titre et la description du document
suivent la langue courante.

## Interface : comment ça marche

```text
src/i18n/
  locales/fr.ts       # catalogue de référence, source des clés
  locales/en.ts       # typé sur MessageKey : une clé manquante casse le typecheck
  index.ts            # getLocale, setLocale, t, interpolation
  useTranslation.ts   # hook React (useSyncExternalStore)
  i18n.test.ts        # parité, placeholders, tirets cadratins
```

Une clé est une chaîne plate, avec des variables entre accolades :

```ts
// fr.ts
'mission.header': 'Mission {number} · {title}',
```

```ts
import { t } from '../i18n';

t('mission.header', { number: 2, title: 'Les 3 zones' });
```

Dans un composant, utiliser le hook pour être re-rendu au changement de langue :

```tsx
const { locale, t } = useTranslation();
```

`t()` est aussi appelable hors React (explications, aide, commandes applicatives) : il lit
la langue courante du module.

### Ajouter une clé

1. Ajouter la clé dans `fr.ts`.
2. Ajouter la même clé dans `en.ts`. Le typecheck refuse l'oubli et les variables
   divergentes sont détectées par `npm run check:i18n`.
3. Utiliser `t('ma.cle')` dans le composant.
4. Ajouter des variables uniquement si elles apparaissent dans les deux catalogues.

### Langue courante

- Au premier lancement, la langue est déduite de `navigator.language` hors tests.
- Le choix est persisté dans `localStorage` sous `gitquest.locale`.
- Sous Vitest, la langue de départ est toujours le français : les tests d'interface
  restent stables.
- Le sélecteur `FR` / `EN` est dans la barre supérieure.

### Ajouter une langue

1. Créer `src/i18n/locales/<code>.ts` avec `Record<MessageKey, string>`.
2. Ajouter le code dans `LOCALES` (`src/i18n/index.ts`) et dans `CATALOGS`.
3. Ajouter le libellé dans `localeNames`.
4. Étendre `ContentPack` si le contenu de cette langue est prêt.
5. Lancer `npm run check:i18n`.

## Contenu : catalogue de textes par langue

Le contenu pédagogique est résolu à l'exécution par `contentFor(locale)`
(`src/content/localized.ts`). Le français reste la source de vérité de la
structure : identifiants, états initiaux, validateurs et commandes vivent dans
`src/content/chapters/`. L'anglais vit dans un catalogue de textes aligné par
position :

```text
src/content/catalogs/
  types.ts             # formes des textes traduits
  en/
    prologue.ts        # leçon de syntaxe
    chapter-01.ts ...  # un fichier par chapitre
    briefings.ts       # récits de mission
    messages.ts        # raisons de validation (français → anglais)
    index.ts           # assemblage du pack
src/content/localized.ts # fusion structure française + textes anglais
src/content/useContent.ts # hook React, rafraîchi au changement de langue
```

`useContent()` s'abonne à la langue : la carte, les cours, les missions, les
briefings et l'arbre Nova se rafraîchissent sans rechargement.

### Ajouter ou modifier un texte anglais

1. Modifier le fichier `src/content/catalogs/en/chapter-XX.ts` correspondant.
2. Garder le même ordre de slides, d'étapes, d'options de prédiction et de
   répliques que le fichier français.
3. Ne jamais traduire : identifiants, commandes, chemins, noms de branches,
   placeholders `{slotId}` et hashes.
4. Lancer `npm run check:content` : les invariants vérifient que les deux packs
   ont les mêmes ids, le même nombre de missions, les mêmes commandes de
   solution et les mêmes nombres de slides, étapes et options.

Les raisons de validation (`check(...)`) restent écrites en français dans les
missions. Le pack anglais intercepte le résultat et les traduit via
`catalogs/en/messages.ts` ; une raison inconnue reste en français et le test de
fuite la signale.

### Ajouter une langue

1. Créer `src/i18n/locales/<code>.ts` avec `Record<MessageKey, string>`.
2. Ajouter le code dans `LOCALES` (`src/i18n/index.ts`) et dans `CATALOGS`.
3. Ajouter le libellé dans `localeNames`.
4. Créer `src/content/catalogs/<code>/` avec les mêmes formes et brancher le
   pack dans `contentFor`.
5. Lancer `npm run check:i18n` et `npm run check:content`.

Les identifiants et les commandes ne se traduisent jamais : seuls les textes changent.
Les hashes restent des placeholders `{slotId}`.

## Ce qui ne se traduit pas

- Les commandes Git (`git switch -c feature`).
- Les messages d'erreur Git fidèles au vrai Git.
- Les noms de branches, de fichiers, de commits d'exemple.
- Les identifiants de missions et de slots.
- Les noms des coéquipiers (Léa, Inès, Yanis, Samir) et leurs rôles restent des données
  de contenu.

## Vérifier

```bash
npm run check:i18n   # clés, variables, tirets cadratins
npm run check:content # invariants des deux packs + test de fuite du français
npm run typecheck    # toute clé anglaise manquante
npm test
```

La règle du projet interdit le tiret cadratin (U+2014), y compris dans les catalogues.
Utiliser une virgule, deux-points, des parenthèses ou un tiret simple.
